<objective>
Cut `v4.0.0` — the one irreversible step in this phase — and verify what it produced.

Two separate events are required, and conflating them is the failure mode this plan
exists to prevent:
- **Pushing the tag** `v4.0.0` fires `.github/workflows/publish.yml`, which runs
  test → build → publish-testpypi → publish and lands the package on PyPI.
- **Publishing a GitHub Release** on that tag is what fires the Zenodo webhook enabled
  in Plan 05. A tag with no Release archives nothing, and Zenodo does not backfill.

Everything reversible has already been done: the version is set, `CITATION.cff` is in
place with no DOI (Pass A), the README is rewritten, both trusted publishers and both
GitHub environments exist, the artifact has been built, strictly checked, and installed
from a clean environment, and the Zenodo webhook is confirmed live on the GitHub side.

Purpose: makes README-04's `pip install aquapose` true and README-02's PyPI badges
real; mints the software DOI that Plan 07 backfills.
Output: a published PyPI release, a GitHub Release, a Zenodo record, and two recorded
DOIs.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tag push → PyPI upload | Pushing a matching tag causes an automated, OIDC-authenticated, irreversible upload under this project's PyPI identity. |
| GitHub Release → Zenodo archive | Publishing the Release causes a permanent public archive and DOI mint under the maintainer's Zenodo identity. |
| PyPI package → every user's machine | From this moment on, `pip install aquapose` executes this project's code on strangers' machines. |
| README long description → PyPI project page | The README shipped in the wheel metadata is served to every PyPI visitor, outside GitHub's link-resolution context. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-06-01 | Tampering | the immutable `aquapose-4.0.0` filenames | mitigate | A defective upload cannot be replaced (D-02's accepted risk). Three controls stand in front of it: Plan 05 Task 2's local build + `twine check --strict` + clean-install; the retained `needs: publish-testpypi` gate, which fails before anything reaches PyPI and is recoverable by deleting and re-cutting the tag; and Task 2's explicit per-failure recovery instructions that forbid editing the workflow to skip the gate. |
| T-114-06-02 | Spoofing | tag-format mismatch producing a silent no-op | mitigate | Cutting the tag with `semantic-release version` on `dev` would produce `v4.0.0-dev.N`, which does not match the trigger — the release would appear to have been made while nothing published, and a later "fix" under pressure is where mistakes happen. | T-114-06-03 | Repudiation | tag pushed but no GitHub Release published | mitigate | Zenodo fires on release publication, not tag push, and does not backfill. A tag-only release would leave the software permanently unarchived with no DOI, and Plan 07 would have nothing to backfill. Residual risk from unpinned third-party actions is recorded in Plan 05 as T-114-05-04. |
| T-114-06-05 | Information disclosure | permanent Zenodo record contents | mitigate | Whatever the Release archives and whatever `CITATION.cff` says is public and permanent.
