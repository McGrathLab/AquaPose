Write `docs/getting-started/concepts.md` as MyST `.md`. It is the "what does this
thing compute" page, read before the tutorial. Cover, in this order:

1. **What AquaPose computes.** One or two paragraphs: from 12 synchronized
   top-down camera views of a tank, AquaPose produces a 3D midline curve per fish
   per frame, with a stable global identity across cameras and time. Name the
   rig concretely using the deposit's provenance: a 12-camera ring at roughly
   0.6 m radius over a 2 m cylindrical tank, cameras pointing straight down
   through a flat air-water interface with no glass, 30 fps, 1600x1200.

2. **Why refraction changes the problem** (D-02, intuition depth only). Explain
   that light from a fish bends as it crosses the flat air-water interface, so
   the straight line from a camera's pixel out into the world is not the path the
   light actually took; standard multi-view triangulation, which intersects
   straight rays, therefore converges on the wrong point underwater. Then say
   what AquaPose does instead: it casts a *refracted* ray, applying Snell's law
   at the interface, and because doing that per pixel per frame is expensive it
   precomputes two lookup tables — a forward table mapping pixel to ray in
   water-space, and an inverse table mapping a voxel of the tank volume to the
   pixel it lands on in each camera, which also yields the camera-overlap graph.
   State that these tables are generated once per camera setup and are not
   shipped with the dataset, and that the pipeline fails fast if they are missing.
   **No derivations.** Do not state the refraction equations, do not give the LUT
   grid formulation, and do not reduce this to "we handle refraction, see the
   API" — both extremes were explicitly rejected in D-02.

3. **The five pipeline stages** (D-03b: these five and nothing else). Open with a
   Mermaid `flowchart` block showing Detection → 2D Tracking → Cross-Camera
   Association → Midline → Reconstruction (D-03a). Then one short subsection per
   stage, each stating what it consumes and what it produces, drawn from
   GUIDEBOOK section 6:
   - *Detection* — per-camera oriented bounding boxes; cameras are processed
     independently; most cameras see zero or few fish in a given frame and that
     is normal, not an error.
   - *2D Tracking* — per-camera tracklets with local track IDs that have no
     cross-camera meaning; per-frame tags distinguish a real detection from a
     coasted prediction.
   - *Cross-Camera Association* — where global fish IDs are assigned and become
     authoritative; built from the camera-overlap graph, ray-to-ray distances,
     and clustering; explicitly handles partial observability (a fish is
     typically seen by only a handful of the 12 cameras) and tracklet
     fragmentation.
   - *Midline* — crops aligned to each detection's oriented box, then either
     segmentation-plus-skeletonization or direct keypoint regression to six
     anatomical points (nose, head, spine1, spine2, spine3, tail); both backends
     emit the same structure, N arc-length-sampled points with optional
     half-widths; a detection that fails extraction produces a flagged empty
     midline rather than an exception.
   - *Reconstruction* — confidence-weighted triangulation using only the cameras
     known to observe that fish, producing one 3D B-spline midline per fish per
     frame, with fish that could not be reconstructed reported with a reason.
   A second Mermaid block showing the `PipelineContext` read/write data flow from
   GUIDEBOOK section 6 is optional (Claude's Discretion) — include it if it earns
   its place.

4. **Identity** — a short subsection: Stage 2 assigns local per-camera IDs,
   Stage 3 assigns the global fish IDs everything downstream uses, and a fish's
   position in a frame's slot list is not its identity.

5. **What comes out: the midline representation** (D-01 — the load-bearing
   section). Document what the pipeline actually produces:
   - Per fish per frame, six anatomical keypoints are sampled along the body at
     fixed arc-length fractions and fitted to a 3D B-spline.
   - The spline is characterized by its degree and its knot vector, plus control
     points. Cite the verified reference schema from the deposit's
     `reference_outputs/outputs.h5`: a single `midlines` group carrying the
     spline degree and an 11-element knot vector as attributes, with datasets for

     `is_low_confidence`. Give the array shapes as they appear in the reference
     file so a reader knows what to expect.
