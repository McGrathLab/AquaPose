## Downstream Consumers (verified against source, Task 2; corrected at Task 3 checkpoint)

An earlier draft of this section claimed the bias was confined to pseudo-label
generation and evaluation, on the strength of one dead parameter. That
understated the blast radius and was corrected before phase close. Confirmed
consumers of `pose.keypoint_t_values`, verified against source:

- **`core/reconstruction/stage.py` (`ReconstructionStage`) — the live
  pipeline, not just training/eval tooling.** `keypoint_t_values` is stored
  in `__init__` (lines 179-183, defaulting to module constant
  `_DEFAULT_KEYPOINT_T_VALUES = [0.0, 0.1, 0.3, 0.5, 0.7, 1.0]` when the
  config value is `None`) and consumed in `run()` at line 310, passed into
  `_keypoints_to_midline` to convert per-camera 2D keypoints into a 3D
  midline before triangulation. It is wired from config via
  `engine/pipeline.py:344` (`keypoint_t_values=config.pose.keypoint_t_values`),
  which is `build_stages`'s real, live wiring. **For any project whose config
  sets `pose.keypoint_t_values` — YH does — the arc-length bias reaches the
  live 3D reconstruction output itself, not only downstream artefacts.**
  Verified `aquapose-tutorial-data/config.yaml` is unaffected because its
  `load_config(...).pose.keypoint_t_values` is `None`, so its
  `ReconstructionStage` uses the uniform-leaning default, not the biased YH
  vector.
- `reproject_spline_keypoints` (`src/aquapose/training/pseudo_labels.py:50-95`)
  and `training/pseudo_label_cli.py` (fails fast if `keypoint_t_values` is
  `None`) — pseudo-label generation.
- `evaluation/tuning.py:974` and `evaluation/runner.py` (~lines 1062-1082,
  falling back to `_DEFAULT_KEYPOINT_T_VALUES` if the run config has no
  value) — evaluation scoring.
- **The one component that genuinely does NOT consume it:** the pose
  *backend* itself, `PoseEstimationBackend.__init__`
  (`src/aquapose/core/pose/backends/pose_estimation.py:59`), accepts a
  `keypoint_t_values` constructor parameter but never references it again —
  `grep -n keypoint_t_values` on that file returns exactly one line. This is
  a real, narrow finding (the neural-net pose backend that predicts 2D
  keypoints per frame ignores the value entirely) but it does not narrow the
  overall blast radius, because `ReconstructionStage` is a separate pipeline
  stage that does consume it, downstream of the pose backend.
