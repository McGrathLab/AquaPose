## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| README to PyPI project page | `pyproject.toml:9` makes this file the published long description. Whatever it says or links to is served to every visitor of the PyPI project page, outside GitHub's rendering and link-resolution context. |
| README to third-party badge providers | Six shields.io image requests are issued by every viewer's browser when the README renders on GitHub and on PyPI. |
| README instructions to a user's machine | The quick start's install and run commands are executed verbatim by strangers. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-04-01 | Spoofing | relative links in the PyPI long description | mitigate | A relative link like `docs/contributing.md` resolves against `pypi.org` on the project page, producing a broken or misleading destination. Task 2's check asserts every Markdown link target starts with `http` and fails with the offending list; a `must_haves` prohibition restates it. |
| T-114-04-02 | Tampering | shields.io as a third-party image host | accept | Six badge images are fetched from `img.shields.io` at render time, and from Codecov/GitHub/RTD upstream of that. A compromised badge provider could serve misleading imagery. This is the universal cost of any badge row; the alternative — self-hosted static badges — trades a live signal for a stale one, which D-04 explicitly rejects. |
| T-114-04-03 | Information disclosure | Codecov badge URL | mitigate | Codecov's `graph/badge.svg` form can carry a per-repo token as a query parameter, which would publish a credential in the README on both GitHub and PyPI. Task 2 specifies shields' `codecov/c/github/...` form, which takes no token. Plan 02's prohibition against recording credentials applies across the phase. |
| T-114-04-04 | Repudiation | badge honesty | mitigate | A badge rendering `unknown`, or pointing at a service that was never linked, misrepresents project health to a researcher deciding whether to trust the tool. Every non-PyPI badge URL is drawn from Plan 02's table of endpoints observed to return 200 with a non-`unknown` label; the two PyPI-sourced badges are explicitly recorded as pending and verified in Plan 06. |
| T-114-04-05 | Tampering | stale CUDA install instruction | mitigate | The removed force-reinstall command tells users to replace their working PyTorch with a specific CUDA build — plausible-looking, currently wrong, and capable of breaking a working environment. Task 1 verifies the pin-free replacement exists in the docs; Task 2's check asserts `download.pytorch.org/whl/cu` appears nowhere in the README. |
| T-114-04-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no packages and adds no dependency. It does advertise `pip install aquapose` — but that name is claimed by this project's own release in Plan 06, and Plan 05's pre-tag verification builds and installs the artifact from the local `dist/` rather than from an index. Name-squatting risk on `aquapose` is handled in Plan 05's threat model. |
