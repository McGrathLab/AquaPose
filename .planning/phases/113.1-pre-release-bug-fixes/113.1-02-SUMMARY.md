# Phase 113.1 Plan 02: init n_animals sentinel and guard type-safety Summary

**`aquapose init` now writes an int `n_animals` sentinel that fails closed with the intended `ValueError`, `load_config`'s guard type-checks before comparing so no non-int value can slip through, and the post-scaffold guidance tells the user to set it as step 1.**

## Accomplishments

- `init_cmd` writes `n_animals: 0` (int, not the string `"SET_ME"`) with a YAML comment hint injected via the same `str.replace` mechanism already used for the `pose:` section, closing the crash on the generated-artifact path (D-12 part 1).
- `load_config`'s `n_animals` guard now type-checks (`isinstance(..., int)`, explicit `bool` rejection since `bool` is an `int` subclass) before comparing, closing the crash and the silent-pass-through on the hand-edited-config path (D-12 part 2).
- `init`'s post-scaffold console guidance leads with "Edit config.yaml -- set n_animals..." as step 1, renumbering the prior three steps to 2-4 (D-13).
- 7 new regression tests: 3 in `test_cli.py` (int sentinel + comment, guidance wording, end-to-end terminal gate), 4 in `test_config.py` (string/null/float/bool guard rejection through both `cli_overrides` and YAML entry paths).

## Non-vacuousness evidence

**Task 1 gate, writer reverted (sentinel restored to `"SET_ME"`):** re-running
`load_config` against the old-style scaffold reproduced the original bug
verbatim:

```
TypeError '<=' not supported between instances of 'str' and 'int'
```

**Task 3 guard, reverted while Task 1's writer fix stayed in place:** with
`git stash` isolating just the guard change, `test_init_generated_config_fails_with_value_error_not_type_error`
still passed. This confirms the guard hardens the hand-edited-config path,
not the scaffold path -- the scaffold already fails correctly on the writer
fix alone.

**Bool `n_animals` before the guard fix** (recorded via a direct `load_config`
call against a YAML file containing `n_animals: true`, prior to the Task 3
commit): the value passed validation silently (`True <= 0` is `False`) and
propagated:

```
n_animals: True <class 'bool'>
association.expected_fish_count: True
```

This confirms the bool-slip-through case was real, not theoretical -- a bool
would have silently changed `expected_fish_count` without any error.
