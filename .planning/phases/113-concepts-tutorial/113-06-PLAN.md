<objective>
Mint the Zenodo DOI for the tutorial deposit (D-04) and finalize the deposit
against it. A DOI is a **one-way door**: once published it is a permanent public
record, a mistake requires publishing a corrected *version*, and the original DOI
keeps resolving to the flawed files forever. That is why this plan runs after the
D-05 corrections (Plan 03) and after the end-to-end verification run (Plan 05),
and why it opens with an explicit human gate.

This plan reserves the DOI and prepares a final, self-consistent tree. The actual
publish action and the tutorial that cites the published record are Plan 07.

Purpose: DATA-03 (the dataset is deposited with a citable DOI) and DOCS-07 (the
tutorial must cite "the published dataset", not a placeholder).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local deposit tree → permanent public record | Files crossing this boundary become immutable and citable. There is no rollback, only a new version. |
| maintainer identity → Zenodo | The record is published under the maintainer's authenticated account; an agent must not perform this action on their behalf. |
| checksum manifest → downloader | The manifest is the only integrity signal a downloader has; it must describe exactly the files that were uploaded. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-113-19 | Tampering | files attached to the Zenodo draft | high | mitigate | The upload list is generated mechanically from the 22-entry manifest, and `finalize_deposit` plus `verify_deposit` run immediately before it, so a transient LUT or run directory cannot be attached by hand. |
| T-113-20 | Elevation of privilege | Zenodo account action | high | mitigate | The publish action is a blocking `checkpoint:human-action` performed by the maintainer in their own authenticated session; no token is issued to an agent and no API credential is stored in the repository. |
| T-113-21 | Repudiation | citation block | medium | mitigate | The reserved DOI is written into the record's own README before upload, so the published artifact cites itself and a downloader can attribute it without consulting an external mapping. |
| T-113-22 | Tampering | `checksums.sha256` versus uploaded files | high | mitigate | The manifest is re-emitted after the DOI edit, so the digest for `README.md` matches the file actually uploaded; a 22 OK verification gates the task. |
| T-113-23 | Information disclosure | metadata entered into the Zenodo form | low | accept | All values are copied from the already-reviewed `zenodo-metadata.json`; the maintainer's name is intentionally public authorship metadata. |
| T-113-SC | Tampering | npm/pip/cargo installs | low | accept | No package-manager install task exists in this plan; no dependency is added, removed or upgraded. |

ASVS level 1; blocking severity: high. T-113-19, T-113-20 and T-113-22 are all mitigated within this plan.
</threat_model>
