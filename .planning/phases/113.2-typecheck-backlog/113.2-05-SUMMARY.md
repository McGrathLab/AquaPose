## Line-310 Verdict (required by plan)

**Question:** Is `self._embeddings.shape[0]` at (baseline) line 310 — now line 312 after this
plan's import addition — a typing artifact or a real path where `self._embeddings` can be
`None` at runtime?

**(a) Guard-block containment.** Confirmed by direct source read before any edit: lines
303–311 (baseline numbering) are all inside one `if npz_path.exists():` block. The
assignment `self._embeddings = npz["embeddings"].astype(np.float32)` happens two lines
before the `logger.info(...)` call whose argument reads `self._embeddings.shape[0]`, with
no intervening branch, early return, or exception path between the two. Line 310 is
genuinely inside the same guard that establishes the assignment — there is no control-flow
route to line 310 within this block that skips the assignment.

**(b) Inferred type of the assignment.** Verified empirically, not by inspection alone: I
inserted a temporary `reveal_type(npz["embeddings"].astype(np.float32))` call and ran
`hatch run typecheck`, which reported:

```
information: Type of "npz["embeddings"].astype(np.float32)" is "Any"
```

I then added a second `reveal_type(self._embeddings)` immediately after the original
(unmodified) assignment line and got:

```
information: Type of "self._embeddings" is "ndarray[tuple[Any, ...], dtype[floating[_32Bit]]] | None"
```

This shows the mechanism directly: `numpy`'s `NpzFile.__getitem__` (and hence
`.astype(...)` chained on its result) has no precise return type in the stubs used here, so
it resolves to `Any`. When a value of type `Any` is assigned to an attribute declared
`NDArray[np.float32] | None`, basedpyright does **not** narrow the attribute to
`NDArray[np.float32]` at the assignment site — because `Any` is compatible with every type
including `None`, the checker conservatively keeps the full declared union in force. The
very next line's `.shape` access on that still-`X | None`-typed attribute is what produces
`reportOptionalMemberAccess`.

To confirm the diagnosis (not just observe the symptom), I tested the prescribed remedy
before applying it for real: binding the loaded array to a local variable with an explicit
concrete annotation (`embeddings_arr: NDArray[np.float32] = npz["embeddings"].astype(np.float32)`)
and assigning that local to `self._embeddings`, then re-running `reveal_type`:

```
information: Type of "self._embeddings" is "ndarray[tuple[Any, ...], dtype[floating[_32Bit]]]"
```

No `| None`. The concrete local annotation gives basedpyright a real (non-`Any`) type to
narrow against, and the None arm drops away — exactly as expected if the original error was
purely a consequence of the `Any`-typed RHS, not a real runtime possibility.

**(c) Conclusion: narrowing artifact.** `self._embeddings` cannot actually be `None` at line
310/312 — the assignment on the immediately preceding line always executes before the read,
within the same guard, and `.astype(...)` never returns `None`. The error existed solely
because basedpyright's narrowing rule for `Any`-typed assignments to `Optional`-declared
attributes is conservative by design (it cannot prove the `Any` value isn't `None`, so it
doesn't narrow). This is the expected outcome CONTEXT anticipated as the likely finding, and
it was verified with source-level evidence (guard containment + two independent
`reveal_type` probes) rather than assumed from the code's shape. **No todo filed** — this is
not the live-defect branch.

The temporary `reveal_type(...)` diagnostic calls were removed before the final edit; they
do not appear in the committed diff.
