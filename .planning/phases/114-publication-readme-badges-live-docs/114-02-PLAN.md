<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo → Read the Docs | RTD clones the repository and executes `.readthedocs.yaml`'s `build.commands` on its own infrastructure. Repo content becomes executed code on a third-party builder. |
| CI → Codecov | `test.yml` sends `coverage.xml` and a repository upload token from GitHub Actions to codecov.io on every push to `main`/`dev`. |
| external DNS/slug namespace → published URL | `pyproject.toml:53` and the future README/PyPI page point at `aquapose.readthedocs.io`, a subdomain in a shared namespace this project does not yet own. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-02-01 | Spoofing | `aquapose.readthedocs.io` subdomain | mitigate | If the `aquapose` slug is owned by an unrelated party, `pyproject.toml:53` and every Plan 04 README link would point at content this project does not control — and the README is also PyPI's long description, so the misdirection would be published. Task 1 instruction 3 requires stopping and reporting rather than silently accepting an alternate slug; Task 3 additionally asserts the served HTML contains AquaPose's own content, so reachability alone cannot pass the gate. |
| T-114-02-02 | Information disclosure | `CODECOV_TOKEN` | mitigate | Task 2 handles a live upload token. The instructions forbid pasting the value into chat, commit messages, or the SUMMARY; the acceptance criteria require the SUMMARY to record only "confirmed" or "re-set", and explicitly forbid recording partial values or length. The `must_haves` prohibitions restate this as a hard rule. |
| T-114-02-03 | Elevation of privilege | RTD build environment | accept | RTD executes `pip install hatch` then `hatch run docs:build` from the repo. A malicious commit to `dev` could therefore run arbitrary code on RTD's builder under this project's RTD account. This is inherent to any docs-as-code hosting and is bounded by RTD's own sandbox; the repo's branch protections and the fact that only the maintainer pushes to `dev` bound it further. No mitigation added this phase. |
| T-114-02-04 | Tampering | `codecov/codecov-action@v5` | accept | The Codecov action is pinned to a major-version tag rather than a commit SHA, so a compromised upstream tag could run attacker code in CI with access to `CODECOV_TOKEN`. D-05 fences this phase to confirming the project link, and `test.yml` is out of scope for edits. Recorded as residual risk; SHA-pinning all third-party actions is a reasonable follow-up hygiene item. |
| T-114-02-05 | Repudiation | badge honesty | mitigate | A badge that renders `unknown` or points at a dead endpoint misrepresents project health to a researcher deciding whether to trust the tool. Task 3's acceptance criteria assert on badge *label text*, not just HTTP status, and require any degenerate result to be recorded as NOT SHIPPABLE. |
| T-114-02-SC | Tampering | npm/pip/cargo installs | accept | This plan adds no dependency. `hatch run docs:build` resolves the pre-existing, already-audited detached `docs` env from `pyproject.toml:88-103`; no new package enters the dependency set, so the package legitimacy gate has nothing to audit. |
</threat_model>
