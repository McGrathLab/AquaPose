<objective>
Put every precondition for the `v4.0.0` release in place, and do the local
verification that D-02 requires in place of a TestPyPI round trip — without tagging
anything.

**The TestPyPI reconciliation (resolved here, explicitly).** D-02 says "publish
straight to PyPI — no TestPyPI dry run." D-03 says `publish.yml` is used unmodified.
But `publish.yml`'s `publish` job declares `needs: publish-testpypi`, so the
unmodified workflow already routes every tag through a TestPyPI upload before the real
one. These are only in tension if D-02 is read as banning TestPyPI entirely; read
against the discussion it rejected *adding a new `workflow_dispatch` dry-run job* and
the sequencing cost that came with it — not this pre-existing, zero-extra-step gate.

**Decision: the `needs: publish-testpypi` edge stays, and `publish.yml` is not
edited.** Consequences, stated plainly so Plan 06 is not surprised:

1. TestPyPI trusted publishing and a `testpypi` GitHub environment are **required
   preconditions**. Without them the `publish-testpypi` job fails and the real PyPI
   upload never runs. This is the concrete extra setup the decision costs.
2. In exchange, the release gets a real dry run for free, which materially reduces
   D-02's accepted risk that a bad first upload permanently burns `v4.0.0` — because a
   failure in the TestPyPI job happens *before* anything immutable is written to PyPI,
   and is recoverable by deleting the tag, fixing, and re-tagging.
3. The alternative — deleting the `needs` edge — was considered and rejected: it is a
   modification to `publish.yml`, i.e. a departure from D-03, made to avoid a
   safety gate, on the one release in this project's history that cannot be redone.

Purpose: the credential, environment, and archival preconditions behind README-02's
PyPI badge and README-04's install line.
Output: four confirmed external-service configurations and a local build that has been
checked and installed, with no tag created.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions → PyPI / TestPyPI | `publish.yml` exchanges a GitHub OIDC token for a short-lived upload credential. The trust anchor is the trusted-publisher record naming owner, repo, workflow filename, and environment. |
| tag namespace → release pipeline | Anyone able to push a tag matching `v[0-9]+.[0-9]+.[0-9]+` triggers a real publish to PyPI under this project's identity. |
| GitHub release → Zenodo | The Zenodo webhook receives release events and archives repository contents into a permanent public record under the maintainer's Zenodo identity. |
| PyPI namespace → every future `pip install aquapose` | Whoever owns the name `aquapose` on PyPI controls what that command installs on users' machines. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-114-05-01 | Spoofing | the `aquapose` name on PyPI | mitigate | `pip install aquapose` is already published in the docs and the Zenodo deposit README (Phase 113 D-09, an accepted and tracked risk). If a third party owns or squats that name, every user who follows the documented install runs someone else's code. Task 1 instruction 1 requires checking both indexes *first* and stopping if the name belongs to a third party, rather than working around it. |
| T-114-05-02 | Elevation of privilege | PyPI upload credential | mitigate | A long-lived API token in repository secrets would grant upload rights indefinitely to anything that can read secrets, and would survive this release. `publish.yml` already uses OIDC trusted publishing (`permissions: id-token: write`, `environment:`), and Task 1 forbids creating a token. The trusted publisher is scoped to one owner, one repo, one workflow filename, and one environment. |
| T-114-05-03 | Tampering | tag-trigger spoofing | accept-with-control | Any actor who can push a matching tag can trigger a real publish. The GitHub `environment:` on the `publish` job is the available control — Task 1 offers adding a required reviewer on the `pypi` environment as an optional manual approval gate. Beyond that, tag-push permission is the boundary, and it is a single-maintainer repository. Residual risk accepted; recorded rather than silently assumed. |
| T-114-05-04 | Tampering | `pypa/gh-action-pypi-publish@release/v1` and `actions/*@vN` in publish.yml | accept | All third-party actions in `publish.yml` are pinned to moving tags rather than commit SHAs, so a compromised upstream tag could execute attacker code in a job holding `id-token: write`. D-03 fences `publish.yml` from edits this phase, so SHA-pinning is out of scope here. Recorded as residual risk and a reasonable follow-up hardening item. |
| T-114-05-05 | Elevation of privilege | `publish.yml` lacks a top-level `permissions:` block | accept | Without an explicit top-level `permissions: contents: read`, the `test` and `build` jobs receive the repository's default `GITHUB_TOKEN` scope, which may be broader than needed. Tightening it is a `publish.yml` edit and therefore a D-03 departure; the mitigation is deferred rather than taken, and the SUMMARY should note it as a hardening follow-up. |
| T-114-05-06 | Tampering | the immutable first upload | mitigate | PyPI filenames are immutable, so a defective `aquapose-4.0.0` can never be replaced (D-02's accepted risk). Two compensations are in place: Task 2's full local build/`twine check --strict`/clean-install checklist, and the retained `needs: publish-testpypi` gate, which means a broken artifact fails on TestPyPI *before* anything reaches PyPI and is recoverable by deleting and re-cutting the tag. |
| T-114-05-07 | Repudiation | Zenodo webhook silently absent | mitigate | A Zenodo toggle that appears enabled but created no GitHub webhook would leave the release unarchived with no DOI, and Zenodo does not backfill releases created before the integration existed — the failure is unrecoverable without cutting another release. Task 3 requires verifying the webhook on the **GitHub** side with a successful delivery, not just trusting the Zenodo UI. |
| T-114-05-08 | Information disclosure | metadata frozen into a permanent record | mitigate | Whatever `CITATION.cff` says at release time is archived permanently and publicly. Task 3's `read_first` and acceptance criteria re-assert that the file carries no `doi` key before the toggle is enabled, so Zenodo cannot ingest a wrong identifier. |
| T-114-05-SC | Tampering | npm/pip/cargo installs | mitigate | Task 2 installs three things: `build` and `twine` into the working environment, and the locally built wheel plus its declared dependency tree into a throwaway venv. `build` and `twine` are the canonical PyPA tools already named by `publish.yml`'s `build` job and by CONTEXT.md D-02, so they are project-sanctioned rather than newly chosen. The wheel is installed **by local path**, never by name from an index — installing `aquapose` by name before publication is precisely the dependency-confusion vector T-114-05-01 describes, and Task 2 forbids it. No package is added to `pyproject.toml`, so the dependency set is unchanged and there is no new package requiring a legitimacy audit. |
