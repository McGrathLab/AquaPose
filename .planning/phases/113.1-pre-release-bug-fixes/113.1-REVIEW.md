## Critical Issues

### CR-01: `calibrate-keypoints` crashes with an unhandled `TypeError` when `pose:` is present but not a mapping

**File:** `src/aquapose/training/prep.py:292-294`

**Issue:** The writer's guard for the canonical `pose:` key only checks key *presence*, not value *type*:

```python
if "pose" not in config_data:
    config_data["pose"] = {}
config_data["pose"]["keypoint_t_values"] = t_values_list
```

If a user's `config.yaml` contains a `pose:` key with no sub-mapping (valid YAML that `yaml.safe_load` parses as `{"pose": None}` — e.g. a bare `pose:` line left as a placeholder, or a partially-filled-in template), `"pose" not in config_data` is `False` (the key exists), so the `{}` initialization is skipped, and the following line raises an unhandled `TypeError: 'NoneType' object does not support item assignment`. The user sees a raw Python traceback instead of an actionable message.

This is directly reproducible via the actual CLI:

```
$ cat config.yaml
project_dir: /path/to/project
n_animals: 1
pose:
$ aquapose --project <name> prep calibrate-keypoints --annotations annotations.json
...
  File ".../src/aquapose/training/prep.py", line 294, in calibrate_keypoints
    config_data["pose"]["keypoint_t_values"] = t_values_list
    ~~~~~~~~~~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^^
TypeError: 'NoneType' object does not support item assignment
```

Notably, the *legacy*-key handling four lines below this defensively guards against exactly this shape (`isinstance(legacy_midline, dict) and "keypoint_t_values" in legacy_midline`), but the new canonical-key writer path this phase introduced does not apply the same defensive check to `pose:`. This inconsistency is evidence the omission is a gap, not a deliberate choice. No test in `tests/unit/test_calibrate_keypoints.py` exercises a null/non-dict `pose:` section, so nothing caught it.

**Fix:**

```python
if not isinstance(config_data.get("pose"), dict):
    config_data["pose"] = {}
config_data["pose"]["keypoint_t_values"] = t_values_list
```

**Outcome: fixed** (commit `5138674`)

Applied the fix exactly as proposed — the guard now matches the type-safe
`isinstance(legacy_midline, dict)` check used four lines below for the
legacy key. Added `test_null_pose_section_is_treated_as_missing` in
`tests/unit/test_calibrate_keypoints.py`, driven through the real
`aquapose` CLI entry point (`CliRunner` + `cli`), using a config with
`pose: None` (the exact shape from `yaml.safe_load("pose:\n")`). Confirmed
RED against the pre-fix code first: `TypeError: 'NoneType' object does not
support item assignment` — the exact predicted traceback — then confirmed
GREEN after applying the fix.

## Warnings

### WR-01: New `UnidentifiedImageError`/`OSError` handling in `_parse_keypoints_yolo` has zero test coverage

**File:** `src/aquapose/training/prep.py:142-149`; `tests/unit/test_calibrate_keypoints.py`

**Issue:** This phase's plan explicitly imported `UnidentifiedImageError` and wrapped `Image.open(img_path)` to skip-with-warning on a corrupt or unreadable sibling image:

```python
try:
    with Image.open(img_path) as im:
        img_w, img_h = im.size
except (OSError, UnidentifiedImageError):
    logger.warning(
        "Could not open image %s for label %s, skipping", img_path, txt_path
    )
    continue
```

`grep -n "UnidentifiedImageError\|corrupt" tests/unit/test_calibrate_keypoints.py` returns nothing — there is no test that writes a corrupt/truncated image file (or an image with a resolvable path but unreadable content) and asserts it is skipped with a warning rather than crashing the whole command. The parallel "missing sibling image" case (`test_label_without_sibling_image_is_skipped_with_warning`) is tested; the "sibling image resolves but fails to open" case is not. This is exactly the edge this phase's own review priorities called out ("what happens on a corrupt or unreadable image ... is it actually handled?") — the code path is present and looks correct on inspection, but is unverified and could silently regress (e.g. a future refactor narrowing the except clause, or accidentally catching too broadly) without any test noticing.

**Fix:** Add a test that writes a `.txt` label with a resolvable sibling path (correct extension, correct directory) but non-image bytes at that path (e.g. `Path(...).write_bytes(b"not an image")`), and asserts the command still succeeds, logs/skips that file, and processes only the remaining valid instances — mirroring `test_label_without_sibling_image_is_skipped_with_warning`.

**Outcome: fixed (test-only)** (commit `cf6b4e3`)

Added `test_corrupt_sibling_image_is_skipped_with_warning`, exactly as
suggested: a resolvable sibling path with `write_bytes(b"not an image")`
alongside one valid image, asserting the command succeeds and processes
only the valid instance (`"Processed 1 annotations"`). This test passed
even against the pre-fix source — confirming the existing
`(OSError, UnidentifiedImageError)` handling was already correct, just
unverified. No source change was made; per the fixer's instructions this
is documented rather than used to justify a rewrite.

### WR-02: `_resolve_sibling_image`/pixel-scaling failure message is misleading when the real cause is corrupted images, not a missing directory

**File:** `src/aquapose/training/prep.py:173-178`

**Issue:** The single failure message covers two different failure modes that `n_resolved == 0` conflates:

```python
if txt_files and n_resolved == 0:
    raise click.ClickException(
        f"No images resolved for any label file in {labels_dir}. "
        "Images are expected under a sibling 'images/' directory "
        "mirroring 'labels/'."
    )
```

`n_resolved` stays at 0 both when no sibling image path *resolves* (missing `images/` dir) and when every resolved image *fails to open* (all corrupt). The message text ("Images are expected under a sibling 'images/' directory...") is only accurate for the first case and would mislead a user debugging a corpus where the images directory exists but every file happens to be corrupt/truncated (e.g. a bad rsync or a botched batch conversion).

**Fix:** Track the two failure counts separately (e.g. `n_unresolved` vs `n_open_failed`) and tailor the exception message to whichever dominates, or at minimum mention both possibilities in the single message (e.g. "...or exist but could not be opened as images").

**Outcome: fixed** (commit `3729360`)

Took the "track separately and tailor" option: added `n_unresolved` and
`n_open_failed` counters, and three message branches (all-unresolved,
all-open-failed, mixed) that each name the actual cause. Control flow
(skip-with-warning, fail only if none resolve) is unchanged per D-09.
Added `test_fails_with_distinct_message_when_all_images_are_corrupt`
(all-corrupt case asserts `"could not be opened"` present) and extended
`test_fails_when_no_label_resolves_an_image` with
`assert "could not be opened" not in result.output` (missing-dir case must
NOT mention corruption) so the test proves the messages are actually
distinguished, not just that a longer message ships. Confirmed RED against
the pre-fix single-message code first (the all-corrupt case's
`"could not be opened"` assertion failed against the generic
missing-directory message), then GREEN after applying the fix.
